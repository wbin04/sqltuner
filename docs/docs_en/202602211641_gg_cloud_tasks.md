# ROLE
You are a Senior Backend Engineer expert in FastAPI, SQLAlchemy, and Google Cloud Platform (specifically Cloud Run and Cloud Tasks).
Your task is to implement the **Asynchronous Task Processing** system for the **SQLTuner** project.

# CONTEXT
- **Project:** SQLTuner (A tool for DB execution, schema sync, and AI SQL optimization).
- **Current Architecture:** FastAPI backend deployed on Cloud Run. Supabase (PostgreSQL) for database.
- **The Problem:** Heavy tasks like calling the Local LLM (via Ngrok) or running the SQLite in-memory Sandbox block the FastAPI event loop, causing timeouts on Cloud Run.
- **The Solution:** Use **Google Cloud Tasks** to decouple the execution. The backend will enqueue a task and return immediately. Cloud Tasks will push the payload to an internal worker endpoint on the same Cloud Run service.

# STRICT CONSTRAINTS (CRITICAL)
1. **NO CELERY/REDIS:** Strictly use `google-cloud-tasks`. Do not implement or suggest Celery, Redis, or RabbitMQ.
2. **NO ICONS/EMOJIS:** Keep the output purely technical.
3. **SECURITY:** The internal webhook endpoint (`/api/v1/internal/worker/...`) MUST verify the Google OIDC token to ensure only Cloud Tasks can call it. Do not leave it open to the public.
4. **LOCAL DEVELOPMENT FALLBACK:** Cloud Tasks cannot reach `localhost`. Implement a fallback mechanism: if `ENVIRONMENT == "local"`, use FastAPI's built-in `BackgroundTasks` to execute the worker function directly. If `ENVIRONMENT == "production"`, use Google Cloud Tasks.
5. **LANGUAGE:** Vietnamese explanations for comments and documentation.

# INSTRUCTION
Generate the code and instructions following this exact structure:

## 1. Database Model (`models.py` or `models/task.py`)
Create a SQLAlchemy model to track task status.
- **Table:** `background_tasks`
- **Columns:**
  - `id`: UUID (Primary Key)
  - `user_id`: UUID (Foreign Key to users)
  - `task_type`: String (e.g., 'llm_optimize', 'sqlite_sandbox')
  - `status`: String (Default: 'PENDING'. Options: 'PENDING', 'PROCESSING', 'SUCCESS', 'FAILED')
  - `payload`: JSON (Input data)
  - `result`: JSON (Nullable, stores the output)
  - `error_message`: String (Nullable)
  - `created_at`, `updated_at`

## 2. Cloud Tasks Service (`services/task_service.py`)
Create a service class/functions to handle task enqueueing.
- **Dependencies:** `google-cloud-tasks`.
- **Function `enqueue_task`:**
  - Parameters: `task_db_id`, `task_type`, `payload`.
  - Logic: Check `settings.ENVIRONMENT`.
    - If `local`: Inject into FastAPI `BackgroundTasks`.
    - If `production`: Construct the Cloud Tasks HTTP request targeting the Cloud Run URL (`settings.BACKEND_URL + "/api/v1/internal/worker"`). Attach OIDC token configuration using `settings.SERVICE_ACCOUNT_EMAIL`. Create the task in GCP.

## 3. Worker & Polling Endpoints (`api/v1/endpoints/tasks.py`)
Implement the API routes.
- **`GET /api/v1/tasks/{task_id}`:**
  - Returns the task status and result. Protect with `get_current_user`.
- **`POST /api/v1/internal/worker` (The Webhook):**
  - **Dependency/Auth:** Verify the Authorization Bearer token (Google OIDC) to ensure the request comes from Cloud Tasks.
  - Parse the payload (extract `task_id`, `task_type`, `data`).
  - Update task status to `PROCESSING` in DB.
  - Route to the correct execution function based on `task_type` (e.g., call LLM via Ngrok or run SQLite).
  - On success: Update DB status to `SUCCESS` and save `result`.
  - On exception: Update DB status to `FAILED` and save `error_message`.
  - Return `200 OK` so Cloud Tasks knows it succeeded.

## 4. GCP Setup Commands (Infrastructure)
Provide the exact `gcloud` commands the user needs to run in their terminal to:
1. Create a Cloud Tasks queue (e.g., `sqltuner-queue`).
2. Create a Service Account for Cloud Tasks to invoke Cloud Run.
3. Grant the Service Account the `roles/run.invoker` permission on the Cloud Run service.
